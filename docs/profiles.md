# Profiles catalog

How country / speed-tier data is built, refreshed, and turned into last-mile shaping and MITM path delay.

## What a profile is

On **Profiles** (and the Inspector status bar) you pick a **country** and a **tier** (`stable` / `typical` / `poor`). That choice becomes:

- **Last-mile** on the WireGuard TUN — delay, loss, download/upload rate via `tc` netem.
- **Path table** — RTT to destinations (`cf`, AWS regions) used by MITM rules for extra API delay after decrypt.

**Direct** (Inspector) clears shaping and path delay (passthrough).

Delay in the product is **one-way** ms. Rough RTT ≈ 2×. Bandwidth: **download** = internet→client, **upload** = client→internet.

## Data sources

Catalog JSON is generated by [`scripts/generate-radar-profiles.py`](https://github.com/kriakiku/potato-inspector/blob/main/scripts/generate-radar-profiles.py) and shipped as:

- `profiles/radar/catalog.json` (pulled by **Profiles → Update catalog from GitHub**)
- `internal/catalog/data/catalog.json` (embedded fallback in the image)

| Source | What it provides |
|--------|------------------|
| [Cloudflare Radar](https://developers.cloudflare.com/radar/) Speed summary | Last-mile: download/upload Mbps, packet loss, idle latency → CF RTT (`rttToDest.cf`) |
| Radar entities / locations | Country list (alpha-2) when a token is present |
| [CloudPing](https://www.cloudping.co/) region↔region latencies | AWS backbone P50 between regions |
| Country capital → AWS coords (haversine) | Nearest AWS region; geo backbone if CloudPing is down |
| Seed tables in the script | Fallback last-mile when Radar misses a country or no API token |

CI: `.github/workflows/radar-profiles.yml` (weekly + **Run workflow**). Needs GitHub secret `CLOUDFLARE_API_TOKEN` with **Account → Radar → Read**. CloudPing needs no secret (`CLOUDPING_URL` defaults to the public API).

Without a Radar token, CI/local runs still build a catalog from seed + CloudPing (`source` like `seed+cloudping`).

## How numbers are calculated

### Last-mile (Radar or seed)

For each country, typical-tier base values come from Radar `quality/speed/summary?location=XX` (or seed):

- `bandwidthDownload` / `bandwidthUpload` → Mbps  
- `packetLoss` → %  
- `latencyIdle` → `rtt_cf` (ms)

Tiers are derived from that typical base:

| Tier | Bandwidth | Loss | RTT table |
|------|-----------|------|-----------|
| `stable` | ×1.25 | ×0.3 (floor 0.05%) | ×0.85 |
| `typical` | as measured | as measured | as measured |
| `poor` | ×0.2 (floors) | ×3 (floor 1%) | ×1.4 |

### Path RTT (`rttToDest`)

1. Pick **nearest AWS** to the country (capital / Radar lat-lon → closest listed AWS dest).
2. For each AWS destination:

   `rtt_dest ≈ rtt_cf + CloudPing(nearest_aws_region, dest_region)`

   Same region → backbone `0`. If CloudPing has no edge, use a geo fiber estimate between region coords.
3. `rttToDest.cf` is just `rtt_cf`. AWS entries are at least `rtt_cf` (never below last-mile to edge).

CloudPing is **region↔region backbone**, not eyeball→AWS. The eyeball leg is modeled as `rtt_cf`.

### Applying a profile (runtime)

When you apply country+tier:

1. **Host baseline** (Baseline page / probe) stores this container’s RTT to `cf` and AWS targets.
2. Last-mile **one-way delay** ≈ `(rttToDest.cf − hostRtt.cf) / 2` (clamped ≥ 0). So you do not double-count the path you already have to Cloudflare.
3. Rate and loss come from the tier (optional global **Disable packet loss** forces loss to 0%).
4. MITM path rules: extra one-way delay for dest D ≈  
   `((rttToDest[D] − rttToDest.cf) − (hostRtt[D] − hostRtt.cf)) / 2`  
   on top of last-mile netem (after decrypt), not a second packet-level path.

## Refreshing the catalog

1. GitHub Actions → **Radar profile catalog** → Run workflow (with `CLOUDFLARE_API_TOKEN` set).
2. On the panel: **Profiles → Update catalog from GitHub** (fetches raw JSON from `main`; no need to rebuild the image for data-only updates).
3. Locally:

```bash
export CLOUDFLARE_API_TOKEN=…   # Account → Radar → Read
python3 scripts/generate-radar-profiles.py
```
